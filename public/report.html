1. Project Overview

The Campus Event Registration & Login System (internally known as EventFlow SQL) is a modern, responsive web application engineered to coordinate, display, and manage university campus events. The system acts as a secure transactions portal enabling students to sign up for seminars, hackathons, sports activities, and cultural festivals while maintaining relational constraints in real-time.

1.1 Real-World Use Case

In a typical university setting, managing events and coordinating registrations are manually intensive, often leading to oversigned events, database errors, or security holes. This project provides a robust digital solution:

  • Students register once, login securely, browse up-to-date events catalogs, check seat availability, and manage registrations.
  • Administrators oversee analytics, create new campus events, monitor seat bookings, and search registries.

1.2 Importance of DBMS in Event Portals

Without a relational Database Management System (DBMS), handling transaction constraints is highly prone to failures (e.g., two students booking the last remaining seat simultaneously). A relational database guarantees ACID properties (Atomicity, Consistency, Isolation, Durability) to ensure capacity counts never exceed physical seat limits, registration lists stay linked to unique student accounts, and student data is preserved securely under foreign key restraints.

5. Backend Working Flows

The backend acts as an orchestrator converting RESTful API HTTP calls into safe, parameterized SQL transactions, returning results in JSON arrays:

  1. Registration Flow: Student sends profile data. Backend checks if the email or USN already exists via a `SELECT` statement. If unique, passwords are encrypted via `bcryptjs`, and records are securely written using a parameterized `INSERT` query.
  2. Login Flow: Student provides email and password. Backend pulls the unique account details using `SELECT * FROM students WHERE email = ?`. Password validation compares the hashes. On success, user parameters are written to the Express session, sending back a secure session cookie (`connect.sid`).
  3. Database Connection Pool: Using a pool rather than opening single connections ensures threads are reused dynamically, protecting database performance.
  4. Event Transaction Safeguards: When registering, the backend performs a check on remaining seats. A SELECT count counts existing signups and compares it with event capacity. If capacity is not exceeded, the registration is authorized.

6. SQL Query Explanation (Line-by-Line Viva Details)

Here are the specific, raw SQL queries integrated into the EventFlow application, designed to clearly demonstrate core DBMS constructs to evaluators:

CONCEPT A: Multi-Table Joins & Student Enrollments 
SELECT s.student_id, s.full_name, s.usn, s.department, r.registered_at 
FROM registrations r 
INNER JOIN students s ON r.student_id = s.student_id 
WHERE r.event_id = 1 
ORDER BY s.full_name ASC;
  • Purpose: Retrieves the list of all students registered for the event with ID = 1.
  • Line 1 (SELECT): Projects specific fields: student's name, USN, department, and exact registration time, omitting password fields for security.
  • Line 2 & 3 (INNER JOIN): Combines records from the junction table 'registrations' (r) and entity table 'students' (s) where the 'student_id' matches in both tables.
  • Line 4 (WHERE): Filters records, returning only registrations matching Event ID = 1 (HackFest 2026).
  • Line 5 (ORDER BY): Sorts student rows alphabetically (A-Z) by full name.
CONCEPT B: Aggregate COUNT, Outer LEFT JOIN & GROUP BY 
SELECT e.event_id, e.title, e.capacity, COUNT(r.registration_id) AS total_registrations 
FROM events e 
LEFT JOIN registrations r ON e.event_id = r.event_id 
GROUP BY e.event_id, e.title, e.capacity 
ORDER BY total_registrations DESC;
  • Purpose: Compiles the metrics display showing active events, seat capacities, and current enrollment counts.
  • COUNT(r.registration_id): Counts registration records associated with each event.
  • LEFT JOIN: Ensures that ALL events are returned, even if they have 0 registrations (an INNER JOIN would omit events with 0 signups!).
  • GROUP BY: Groups results by event details so aggregate counts are computed per event.
  • ORDER BY DESC: Sorts events by popularity, placing the highest registration counts first.
CONCEPT C: GROUP BY Filtering with HAVING Clause 
SELECT e.event_id, e.title, COUNT(r.registration_id) AS total_regs 
FROM events e 
INNER JOIN registrations r ON e.event_id = r.event_id 
GROUP BY e.event_id, e.title 
HAVING total_regs >= 2;
  • Purpose: Identifies high-interest events having 2 or more registrations.
  • HAVING Clause: Standard 'WHERE' filters cannot evaluate aggregate functions. We use 'HAVING' to filter grouped records based on computed COUNT aggregates.
  • Viva Rationale: 'WHERE' filters individual database rows *before* grouping; 'HAVING' filters grouped datasets *after* aggregation has run!
CONCEPT D: Nested Subqueries & NULL checks 
SELECT student_id, full_name, usn, department 
FROM students 
WHERE student_id NOT IN (
    SELECT DISTINCT student_id 
    FROM registrations
);
  • Purpose: Searches the roster to list inactive students who have signed up for 0 events.
  • Subquery (SELECT DISTINCT): Compiles a unique set of all student IDs present in registrations.
  • NOT IN: The outer query returns student profiles whose IDs do *not* appear in the subquery's list.

7. Security & Authentication Flow

Securing user records is critical to modern application integrity. This project implements standard cryptographic safeguards:

  • Password Cryptography (bcryptjs): Plaintext passwords are never stored in the database. When creating an account, the password is encrypted using a SHA-256 salt-based algorithm (salt rounds = 10).
  • Session Cookies: Rather than passing sensitive IDs back and forth, a secure session cookie (`connect.sid`) is saved in the browser. The session data is maintained safely on the server.
  • Input Injection Guard: Sanitization protects the database against SQL injections. We use parameterized queries where inputs are parsed as string literals rather than raw executable code.

9. Viva Preparation Q&A (Be Viva-Ready!)

Here are the most frequently asked questions during database and web project viva evaluations, along with clear, technical answers:

Q1: Explain the difference between INNER JOIN and LEFT JOIN. Which one did you use and why?
Answer: An INNER JOIN returns rows only when there is a match in both joined tables. If a student has no registrations, they will not appear. A LEFT JOIN returns ALL rows from the left table, along with matching rows from the right table. If there is no match, the columns of the right table return NULL.
In this project, we used LEFT JOIN to show all events (including those with 0 signups) on the catalog, and INNER JOIN for the registration log to only list active event bookings.
Q2: How does your junction table handle composite unique keys? Why is it important?
Answer: Our junction table registrations features a composite unique constraint: CONSTRAINT unique_registration UNIQUE (student_id, event_id). This ensures that the database rejects any attempt to insert a duplicate combination of the same student and event. This constraint prevents double-registrations, maintaining relational integrity.
Q3: What is SQL Injection, and how did you prevent it in your code?
Answer: SQL Injection is a vulnerability where an attacker embeds malicious SQL commands into input fields, aiming to manipulate or drop tables. We prevent this by using parameterized queries (using the ? placeholders in mysql2). Parameters are parsed by the database as data literals, not executable code, neutralizing injection attempts.
Q4: What are the normalization forms, and is your database normalized?
Answer: Yes, our database is designed in **Third Normal Form (3NF)**.
  • 1NF: All values are atomic (each cell contains one value) and columns contain values of the same type.
  • 2NF: It is in 1NF and contains no partial dependencies (non-key columns depend entirely on the primary keys).
  • 3NF: It is in 2NF and contains no transitive dependencies (non-key columns do not depend on other non-key columns).
Q5: Explain the 'ON DELETE CASCADE' clause. What happens if a student account is deleted?
Answer: The ON DELETE CASCADE constraint ensures that when a parent record is deleted, all child records referencing it are deleted automatically. In our system, if an event or a student is deleted, all associated registrations in the junction table are removed automatically. This prevents orphan records and preserves referential integrity.
Q6: What is a Correlated Subquery? How is it different from a standard subquery?
Answer: A standard subquery is independent of the outer query and runs once. A correlated subquery is dependent on the outer query, referencing columns from the outer query's current row. It runs repeatedly, once for every row processed by the outer query. We use this concept to list fully booked events by dynamically comparing the event's capacity to its real-time registration count.
